# Contributing

Keep shared workflow behavior independent of a specific harness. Place native
integration details in command/agent adapters and document capability limits.
Use the live MCP schema for parameter changes; examples must not assume that a
tool is deployed everywhere.

Use the [development commands](README.md#development) before submitting changes.
New executable behavior needs focused regression coverage. Run native validation
when the CLI is available:

```sh
claude plugin validate ./plugins/agent-task
claude plugin validate .
```

Keep credentials and generated crew data out of commits. Preserve existing user
instructions, hooks, and client configuration. Never add a networked hook that
silently performs task mutations with an organization API key.

## Versioning and releases

`plugins/agent-task/.claude-plugin/plugin.json` is the version source.
The Codex manifest is generated by `scripts/sync_metadata.py`; marketplace
entries intentionally omit versions. To prepare a release:

1. Update the canonical manifest version and `CHANGELOG.md`.
2. Run `python3 scripts/sync_metadata.py`, validation, unit tests, and ShellCheck.
3. Review the complete diff, including compatibility and security implications.
4. After approval, commit and create an annotated `vX.Y.Z` tag for that commit.
   Push the reviewed branch/tag through the canonical repository's release process.
5. Verify installation and OAuth in the intended client versions before announcing
   broader compatibility. A local validator is not an authentication smoke test.

CI checks tag/version agreement when running on a version tag. Release preparation
does not itself publish, tag, install globally, or mutate a user's plugin cache.
